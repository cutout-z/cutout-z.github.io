Why Your "AI-First" Strategy Is Probably Wrong

99% of our production code is written by AI. Last Tuesday, we shipped a new feature at 10 AM, A/B tested it by noon, and killed it by 3 PM because the data said no. We shipped a better version at 5...

We didn't get here by adding Copilot to our IDE. We dismantled our engineering process and rebuilt it from scratch.

CREAO is an agent platform. Twenty-five employees, 10 engineers. We started building agents in November 2024.

OpenAI published a concept in February 2026 that captured what we'd been doing. They called it harness engineering.

We arrived at that conclusion on our own. We didn't have a name for it.

AI-First Is Not the Same as Using AI

Most companies bolt AI onto their existing process. An engineer opens Cursor. A PM drafts specs with ChatGPT. A designer uses Midjourney. The workflow stays the same.

That is AI-assisted.

AI-first means you redesign your process, your architecture, and your organization around the assumption that AI does the building.

You stop asking "how can AI help our engineers?" and start asking

"how do we restructure everything so AI does the building, and engineers provide direction and judgment?"

The difference is multiplicative.

I see teams claim AI-first while running the same sprint cycles, the same Jira boards, the same weekly standups, the same two-week reviews.

A common version of this is what people call vibe coding. Open Cursor, prompt until something works, ship it.

Why We Had to Change

Last year, I watched how our team worked and saw three bottlenecks that would kill us.

The Product Management Bottleneck

Our PMs spent weeks researching, designing, specifying features. Product management has worked this way for thirty years.

It doesn't make sense to think about something for months and then build it in two hours.

PMs needed to evolve into product-minded architects who work at the speed of iteration, or step out of the way.

The QA Bottleneck

Same dynamic. After an agent shipped a feature, our QA team spent days testing corner cases. Build time was two hours. Test time was three days.

We replaced manual QA with AI-built testing platforms that test AI-written code. Validation has to match the speed of creation.

The Headcount Bottleneck

Our competitors had 100x or more people doing comparable work. We have 25. We couldn't hire our way to scale.

Three systems needed AI running through them: how we design product, how we implement product, and how we validate product.

The Bold Decision: Unifying the Architecture

I had to fix the codebase first.

Our old architecture was scattered across multiple independent systems. A single change might require touching five separate repositories. Agents struggled to reason across the full system.

I had to unify all the code into a single monorepo. One reason: so AI could see everything.

This is a harness engineering principle in practice. The more of your system you pull into a form that an agent can ingest and reason about, the more capable the agent becomes at working in that system.

I spent one week designing the new system: planning stage, implementation stage, testing stage, integration stage. Then I handed it to the agents.

CREAO is an agent platform. We used our own agents to rebuild the platform that runs agents. If the system breaks, we eat our own dog food.

The Stack

Here is our stack and what each piece does.

Infrastructure: AWS

We run on AWS with auto-scaling container services and circuit-breaker rollback. If metrics degrade below threshold, the system auto-rolls back without human intervention.

CloudWatch is the central nervous system. Structured logging across all services, over 25 alarms, custom dashboards for every team function.

CI/CD: GitHub Actions

Every code change passes through a six-phase pipeline:

Verify CI → Build and Deploy Dev → Test Dev → Deploy Prod → Test Prod → Release

The CI gate on every pull request enforces typechecking, linting, unit and integration tests, Docker builds, and security scanning. Nothing merges without passing all of it.

AI Code Review: Claude

Every pull request triggers three parallel AI review passes using Claude Opus 4.6:

Pass 1: Code quality. Logic errors, performance issues, maintainability.

Pass 2: Security. Vulnerability scanning, authentication boundary checks, injection risks.

Pass 3: Dependency scan. Supply chain risks, version conflicts, license issues.

These are review gates, not suggestions. They run alongside human review, catching what humans miss at the speed of a CI check.

Engineers also tag @claude in any GitHub issue or PR for implementation plans, debugging sessions, or code analysis. The agent responds in context.

The Self-Healing Feedback Loop

This is the centerpiece.

Every morning at 9:00 AM UTC, an automated health workflow runs. Claude Sonnet 4.6 queries CloudWatch metrics from the prior 24 hours, scans for anomalies, and generates a system health report.

One hour later, the triage engine runs. It clusters production errors from CloudWatch and Sentry, scores each error by severity and customer impact, and creates structured Linear issues with reproduction steps and investigation context.

The system deduplicates. If an open issue covers the same error pattern, it updates that issue. If a new pattern emerges, it creates a new one.

When an engineer pushes a fix, the same pipeline handles it. Three Claude review passes evaluate the fix. If it looks wrong, the engineer hears why before the code merges.

Each tool handles one phase. No tool tries to do everything. The daily cycle creates a self-healing loop: detect, triage, fix, verify.

I told a reporter from Business Insider: "AI will make the PR and the human just needs to review whether to accept it."

Feature Flags and the Supporting Stack

Statsig handles feature flags. Every feature ships behind a gate. The rollout pattern: enable for the internal team first, then percentage rollout, then full release. If metrics degrade at any stage, the gate closes.

Graphite manages PR branching: merge queues rebase onto main, re-run CI, merge only if green. Stacked PRs let agents work on multiple layers simultaneously.

Sentry reports structured exceptions across all services, merged with CloudWatch by the triage engine.

How a Feature Moves from Idea to Production

New Feature Path

  1. The architect defines the task as a structured prompt with codebase context, goals, and constraints.
  2. An agent decomposes the task, plans implementation, writes code, and generates its own tests.
  3. A PR opens. Three Claude review passes evaluate it. A human reviewer checks for strategic risk, not implementation details.
  4. CI validates: typecheck, lint, unit tests, integration tests, end-to-end tests.
  5. Graphite's merge queue rebases, re-runs CI, merges if green.
  6. Six-phase deploy pipeline promotes through dev and prod with testing at each stage.
  7. Feature gate turns on for the team. Gradual percentage rollout. Metrics monitored.
  8. Kill switch available if anything degrades. Circuit-breaker auto-rollback for severe issues.

Bug Fix Path

  1. CloudWatch and Sentry detect errors.
  2. Claude triage engine scores severity, creates a Linear issue with full investigation context.
  3. An engineer investigates. AI has already done the diagnosis. The engineer validates and pushes a fix.
  4. Same review, CI, deploy, and monitoring pipeline.
  5. Triage engine re-verifies. If resolved, ticket auto-closes.

Both paths use the same pipeline. One system. One standard.

The Results

Over 14 days, we averaged three to eight production deployments per day. Under our old model, that entire period might have produced two releases.

Bad features get pulled the same day they ship. New features go live the same day they're conceived.

People assume we're trading quality for speed. User engagement went up. Payment conversion went up. Error rates went down.

The New Engineering Org

Two types of engineers will exist.

The Architect

One or two people. They design the standard operating procedures that teach AI how to work. They build the testing harness. They set constraints. They define the system.

This role requires deep critical thinking. You criticize AI. You don't follow it. When the agent proposes a path, you evaluate whether it's right.

I have a PhD in physics. The most useful thing my PhD taught me was how to question assumptions, stress-test reasoning, and find where logic breaks. That's what this role requires.

This is also the hardest role to fill.

The Operator

Everyone else. The work matters. The structure is different.

AI assigns tasks to humans. The triage system finds a bug, creates a ticket, surfaces the diagnosis, and points the engineer at the likely fix. The engineer validates. The engineer reviews the PR. The engineer confirms.

The tasks are bug investigation, UI refinement, CSS improvements, PR review, verification. They require judgment, taste, and ownership. They do not require writing code from scratch.

Who Adapts Fastest

I noticed a pattern I didn't expect. Junior engineers adapted faster than senior engineers.

Junior engineers with less traditional practice felt empowered. They had access to tools that amplified them far beyond what experience alone would have given.

Senior engineers with strong traditional practice had the hardest time. Two months of their work could now be done in a day. The multiplier is also a threat.

I'm not making a judgment. I'm describing what I observed. In this transition, adaptability matters more than seniority.

The Human Side

Management Collapsed

Two months ago, I spent 60% of my time managing people. Aligning priorities. Running meetings. Giving feedback on implementation decisions.

Today: below 10%.

The traditional CTO model says to empower your team to do architecture work, train them, delegate. That model collapses when AI can do the architecture work.

More stressful. But I'm enjoying building, not aligning.

Less Arguing, Better Relationships

My relationships with co-founders and engineers are better than before.

Before the transition, most of my interaction with the team was alignment meetings. Discussing tradeoffs. Debating implementation. Negotiating priority.

Now I still talk to my team. We talk about other things. Non-work topics. Casual conversations. Offsites. The relationship became human again because the work relationship became transactional in the best way: here is the task, here is the output.

Uncertainty Is Real

I won't pretend everyone is happy.

When I stopped talking to people every day, some team members felt uncertain. What does the CTO not calling me mean? Am I being managed out?

Some people spend more time debating whether AI can do their work than doing the work. The transition created anxiety for people who measured their value by implementation skill.

I do have a principle: we don't fire an engineer because they introduced a production bug. We improve the system so that class of bug can't reach production. The same logic applies to the transition.

Beyond Engineering

I see other companies adopt AI-first engineering and leave everything else manual.

If engineering ships features in hours but marketing takes a week to announce them, marketing is the bottleneck. If sales can't process leads at the speed of growth, sales is the bottleneck.

At CREAO, we pushed AI-native operations into every function:

  • Product release notes: AI-generated from changelogs and feature descriptions.
  • Feature intro videos: AI-generated motion graphics.
  • Daily posts on socials: AI-orchestrated and auto-published.
  • Health reports and analytics summaries: AI-generated from CloudWatch and production databases.

Engineering, product, marketing, and growth run in one AI-native workflow. If one function operates at traditional speed, that function becomes the ceiling.

What This Means

For Engineers

Your value is moving from code output to decision quality. The ability to write code fast is worth less every month. The ability to evaluate whether something is right is worth more.

Product sense or taste matters. Can you look at a generated UI and know it's wrong before the user tells you? Can you read an agent-proposed architecture and see where it will fail under load?

I tell our 19-year-old interns: train critical thinking. Learn to evaluate arguments, find gaps, question assumptions. That skill compounds.

For CTOs and Founders

If your PM process takes longer than your build time, start there.

Build the testing harness before you scale agents. Fast AI without fast validation is fast-moving technical debt.

Start with one architect. One person who builds the system and proves it works. Onboard others into a working system, not an experiment.

Push AI-native into every function.

Expect resistance. Some people will push back.

For the Industry

OpenAI, Anthropic, and multiple independent teams converged on the same principles: structured context, harness engineering, agents with constraints and checkpoints.

Model capability is the clock driving this. I attribute the entire shift at CREAO to the last two model generations. Without Claude Sonnet 4.6 and Opus 4.6, the self-healing loop doesn't work.

I believe one-person companies will become common. If one architect with agents can do the work of 100 engineers, the economics of company formation change entirely.

We're Early

Most founders and engineers I talk to still operate the traditional way. Some think about making the transition. Very few have made it.

A reporter friend told me she'd talked to about five people on this topic. She said we were further along than anyone else she'd spoken to.

The tools exist for any team to do this. Nothing in our stack is proprietary.

The competitive advantage is the decision to redesign everything around these tools, and the willingness to absorb the short-term disruption of a full process rebuild.

We absorbed that cost. Two months later, the numbers speak.

We build an agent platform. We built it with agents.
